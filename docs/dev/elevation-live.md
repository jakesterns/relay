# The elevated install helper — how it works and how to exercise it

`relay-elevate.exe` is the only Relay binary that writes `HKLM`. Everything
else — the core, the UI, the share engine — runs with the user's ordinary
token and stays that way.

There are exactly two things that need it, and both were forced by the same
fact: the service that has to load the DLL runs as `NT AUTHORITY\LocalService`
and cannot see per-user classes.

| Component | Loaded by | Why HKLM | Evidence |
|---|---|---|---|
| Endpoint APO | `audiodg.exe` | audiodg is LOCAL SERVICE | M3b plan, "Install" checklist item |
| Camera media source | Frame Server (`svchost`) | `IMFVirtualCamera::Start` → `0x80070003`; the service never loads the DLL | S5, `docs/dev/vcam-live.md` |

## The shape of it

```
 core (unelevated)                       relay-elevate.exe (elevated)
 ─────────────────                       ────────────────────────────
 1. ElevationPlan  ── read-only ──▶  plan_lines(): the exact listing
 2. show the user the listing
 3. RunElevated
      write data\elevate\<nonce>.request.json
      ShellExecuteExW("runas", …)  ────▶  UAC prompt (the user's decision)
                                          vet: version, age, location, token
                                          vet: COM keys ⊂ our own CLSID
                                          arm one gate, one call, disarm
                                          write <nonce>.result.json
      ◀──────────── wait, read, delete ── exit
 4. show the result lines, re-probe status
```

The request carries **no** registry path, value or DLL path — only a version,
a nonce, a timestamp, the data root and a list of ops from a four-variant
enum. Everything else the helper derives itself, from the same planners the
dry run used and from its own directory. That is what makes "performs exactly
the steps the components recorded and nothing else" true rather than
aspirational: there is no field in the protocol capable of saying anything
else.

The two live-write gates (`RELAY_APO_ALLOW_LIVE_WRITE`,
`RELAY_VDEVICE_ALLOW_LIVE_WRITE`) still guard every write. The helper arms one
of them around one vetted call and removes it immediately after. Nothing else
in the product arms them, so a stray call from a test, a debug session or a
future refactor still fails loudly.

Note for anyone tempted to pass the gates down from a parent: **you cannot.**
Elevation through `runas` starts the child from the user's logon environment
block, not from the parent's environment. That is the bug this session fixed
in the uninstaller's elevated phase, which had been setting the variables in
the parent and wondering why the child refused.

## From the command line

```powershell
# Read-only. Prints exactly what would change; touches nothing.
relay-core elevate plan install-apo
relay-core elevate plan install-camera
relay-core elevate plan uninstall-apo
relay-core elevate plan uninstall-camera

# Raises one UAC prompt, then runs it. Declining prints one sentence and
# changes nothing.
relay-core elevate run install-camera
```

`relay-core uninstall` uses the same helper for its two HKLM steps.

## From Settings

Both opt-in cards use the same panel: **Install… / Remove…** shows the plan
(no prompt yet), and only the **Install now / Remove now** button elevates.
The listing for the two removal directions is the uninstall card's own
listing, narrowed to that step — so what the card promises is generated by the
code that does the removing.

## Live pass on a real machine

Everything below is read-only until the step that says otherwise. Run it from
a normal (non-elevated) shell; the prompt is the only elevation.

1. **Before.** Save what the diff will be measured against:

   ```powershell
   $cam = "HKLM\SOFTWARE\Classes\CLSID\{9B7E62D4-2A31-4C8E-8F5A-D0C4B6E91A27}"
   $apo = "HKLM\SOFTWARE\Classes\CLSID\{5A8E9C3B-1F6D-4B0A-9C41-7E2D83A6F0B4}"
   $fx  = "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\MMDevices\Audio\Render\<endpoint>\FxProperties"
   reg query $cam ; reg query $apo          # both must say "unable to find"
   reg export $fx fx-before.reg /y
   ```

2. **Refusals first**, so the gates are known good before anything is armed:

   ```powershell
   cargo test -p relay-core --test elevate_helper --test elevate_ipc
   ```

3. **Camera round trip.** Record consent, then run it:

   ```powershell
   relay-core vdevice consent-camera
   relay-core elevate plan install-camera     # read this before approving
   relay-core elevate run install-camera      # approve the prompt
   reg query $cam /s                          # two keys, InprocServer32 → the DLL
   relay-core elevate run uninstall-camera    # approve the prompt
   reg query $cam                             # gone
   ```

4. **APO round trip.** Same shape. Do **not** restart `audiosrv` in between:
   an endpoint reloads its FX chain when a stream starts, so without that
   restart the (as yet unsigned) DLL is never handed to audiodg at all, and the
   test stays a registry round trip.

   ```powershell
   relay-core elevate plan install-apo
   relay-core elevate run install-apo         # approve the prompt
   reg query $apo /s
   relay-core elevate run uninstall-apo       # approve the prompt
   reg export $fx fx-after.reg /y
   fc.exe fx-before.reg fx-after.reg          # must be identical
   ```

   Installing the APO *and* restarting `audiosrv` — that is, actually loading
   it into the audio engine — still needs a test-signing VM and the EV
   certificate. M3b deferred item 2, runbook `docs/dev/apo-testsign.md`.

5. **Decline.** Run any `elevate run` and dismiss the prompt. Expect exactly:

   ```
   Nothing on this PC was changed. You declined the Windows permission prompt.
   ```

   and an unchanged registry.

## Results — 2026-09-14, this dev machine

Windows 11 Pro 26200, default render endpoint
`{f8ae226b-a4e3-45ab-97fc-3977dad232d1}` (Headphones, RODECaster Duo
Secondary) — the endpoint with a real vendor FX chain, which is why it is also
the M3b uninstall-diff fixture.

Seven UAC prompts, driven from the Settings cards in a `pnpm tauri dev` build
against a scratch data root, with the installed core stopped for the duration.
The machine ended byte-identical to how it started.

| Step | Result |
|---|---|
| Camera install | `HKLM\...\CLSID\{9B7E62D4-...}` + `\InprocServer32` → the DLL, `ThreadingModel=Both`. Card: *Register the virtual camera: done — "Relay Camera" registered* |
| Camera remove | both keys gone, `installed.json` components back to `[]` |
| APO install | the three PKEYs on the endpoint's `FxProperties`, plus our CLSID key. **The diff against the pre-install export was exactly three added values and nothing removed** — the vendor chain was appended to, never evicted |
| APO remove | `reg export` after is **byte-identical** to before (same SHA-256), CLSID gone |
| Decline | *Nothing on this PC was changed. You declined the Windows permission prompt.* Camera stayed registered, registry unchanged, core log: `UAC prompt declined; nothing was changed` |

### The thing that did not work first time

The first elevated APO install failed with **Win32 error 5** (`ERROR_ACCESS_DENIED`)
even with a full administrator token. The endpoint's `FxProperties` key is
owned by `NT AUTHORITY\SYSTEM` and its DACL gives:

```
NT SERVICE\Audiosrv             SetValue, CreateSubKey, Delete, ReadKey
NT SERVICE\TrustedInstaller     FullControl
NT SERVICE\AudioEndpointBuilder SetValue, CreateSubKey, Delete, ReadKey
BUILTIN\Administrators          SetValue, ReadKey        ← no CreateSubKey
```

`RegCreateKeyExW(..., KEY_WRITE, ...)` asks for `KEY_SET_VALUE |
KEY_CREATE_SUB_KEY`, so it is denied on a key administrators may perfectly
well *write values to*. The fix is to ask for less, not to take more:
`livereg::Key::create` now opens an existing key with `KEY_SET_VALUE` and only
falls back to creating (which needs the parent's `CreateSubKey`) for keys that
do not exist yet — our own CLSID keys under `SOFTWARE\Classes`, where
administrators do have it.

Taking ownership of that key would also have "worked", and would have left the
machine permanently different. That is the opposite of what Relay promises, so
it was never on the table.

The failed attempt is worth keeping in mind for another reason: it left the
install backup on disk, so the next attempt refused with *"a backup for … already
exists — the APO looks installed"*. A failure that reads like a success is its
own bug. `install_live` now reconciles the endpoint to the backup and deletes
the file when the apply fails, and keeps the file (saying so) only when the
rollback itself fails.

### Cost

`relay-elevate.exe` is **0.32 MB** release and nothing stays resident — it runs
for about two seconds and exits. The always-on core grew from 1.31 MB to
**1.47 MB** (the elevate module plus its launcher); the footprint gate after
this session reads **6.76 MB peak RSS, 0.89 MB private working set, 0 % CPU
over 35.6 s** against a 10 MB / 0.5 % budget. PASS.

### What this does *not* prove

The APO was registered and unregistered; it was never **loaded**. `audiosrv`
was deliberately not restarted, so audiodg never tried to bind the (unsigned)
DLL. Loading it into the audio engine still needs test-signing and, for
production, the EV certificate — M3b deferred item 2,
`docs/dev/apo-testsign.md`.
