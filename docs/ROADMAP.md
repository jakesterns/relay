# Relay roadmap (agreed 2026-09-09)

Milestones are sized so one Claude Code session can complete a milestone or a
clearly bounded slice of one. Each milestone has its own plan file under
`docs/plans/` with a kickoff prompt; one chat session per milestone. This file
is the index, the ordering, and the decision log.

## Decisions (2026-09-09)
1. **Share first.** M4 starts right after M0. Display (M2) and audio DSP (M3) run in parallel after that; M1 (hardware probe) lands before M2 needs it.
2. **Latency and efficiency are the top priority for share.** Media Foundation is the first encoder path; if it cannot hold the <50 ms / ~0 CPU targets, direct NVENC follows immediately rather than later.
3. **Receiver is a mode of the same app**, not a separate binary.
4. **EV certificate procurement starts now**, in parallel with M0. APO (M3b) and the virtual mic (M5) are gated on it.

## Sequence
```
M0 foundation ──► M4 share MVP ──► M1 hardware ──► M2 display ──► M3b APO ──► M5 vdevices ──► M6 ──► M7
                                  └► M3 audio DSP (parallel with M1/M2)
EV cert (external) ─────────────────────────────────────────────► unblocks M3b, M5
```

Milestone numbers are stable identifiers; the sequence above is the order of work.

**S35 correction, 2026-09-23 — the identity is the certificate, not the key.** Writing the deferred DPAPI wrap, the new test compared *fingerprints* across two loads of the same file rather than file bytes, and they differed: `RTCCertificate::from_key_pair` mints a fresh self-signed certificate — random serial, random subject — on every call, and the fingerprint hashes the certificate. So every r-build from r12 to r17 had a different DTLS fingerprint on every share, and a remembered peer could never have been recognised; the two-PC pass S35 owed would have found it as "asks for a code every time". Fixed by storing the whole certificate in rtc's own PEM (`serialize_pem` / `from_pem`, its documented persistent-identity path) and, on Windows, wrapping that file with DPAPI in user scope as `identity.key` — the §4 item, now done: a copied file is inert elsewhere and the copier holds nothing. A key-only `identity.pem` from r12–r17 upgrades in place on first read and a plaintext file is wrapped and removed, both with the fingerprint held from that point. Running the fixed engine on a headless loopback then found the second half: `signal::sdp_fingerprint` looked for an `a=fingerprint:` line in what was actually the JSON session description, so it returned nothing at every call site and `remember` was never reached — the only test it had used raw SDP. It now reads either form. `scripts/trusted-check.sh` proves the whole path on one PC: code pairing writes the entry, a no-code share reports `trusted=true` at both ends, a stranger's fingerprint is refused before DTLS. 7 identity tests (was 3), one signalling test on the real wire form; 186 capture, clippy `-D warnings`, footprint green. Record: `docs/dev/trusted-peers.md` §4 and §8, BUGS B17.

**S38, 2026-09-22 — stream resilience: crash record, auto-reconnect, resume.** Jake's requirement: if Relay or a share dies, bring it back by default rather than leaving the user to rebuild it mid-stream; keep the crash log; say what is happening. Built the day S35 merged, because it could not exist before: a share only resumes without a code if the two PCs already remember each other. The core now keeps an **intent record** (`active-stream.json`) for a share or receive the user started and has not stopped; a deliberate Stop clears it *before* the engine is killed, so the exit that follows reads as "stopped", and any other exit reads as "died" and starts a reconnect episode — backoff 1 → 2 → 5 → 10 s, giving up after three minutes, a pure schedule with a unit test. A sender respawns from the recorded request with the receiver looked up by *name* in the remembered-PCs store (so a code pairing resumes with no code, and a peer that is neither remembered nor coded is a dead end that says so); a receiver respawns with the *same pairing code*, so a code-paired sender can come back too. On start the core acts on a leftover record — a crash, a power cut, a reboot — as attempt one, which needs only autostart or the user opening Relay; if both PCs rebooted, each one's record brings its own end back. Every binary now installs a panic hook writing `logs\crash\<ts>-<binary>-panic.txt`, and the core writes one for an engine exit it did not ask for, with the last 50 lines of `share.log`; the next start puts one sentence about the newest unseen record into `CoreState.last_crash`, shown once in the shell with an OK that marks it seen. The tray gained balloons (`NIF_INFO`, posted to the loop thread that owns the icon), used once per episode — dropped, back, gave up, restored after a restart — and for the close notice: the shell tells the core `WindowClosed` and the core says "Relay is still running here" by the clock, every time, until turned off. Two `settings.json` switches, `resilience` and `close_notice`, both default on, both read as on from a file that predates them (the standing rule, tested); the Settings screen now sends the whole preferences object on every toggle, because a partial write would have reset the others. UI: the Share pill reads "Reconnecting (n)…" and keeps Stop; the Receive video area says "The share from X dropped — waiting for it to come back…" — derived from the fact that Start receiving by hand clears the last sender's name and an automatic restart does not, so no new protocol field was needed. Tests: 7 on the record and schedule, 4 on crash records, 1 on prefs, 8 UI (reconnecting pill, dropped text, both toggles, the crash banner); 292 UI, 214 core, 176 capture; fmt, clippy `-D warnings`, footprint green. **Owed: the two-PC pass** — kill the sender's engine by its own PID and watch the share return without a code; the same for the receiver; a reboot of one PC, then both. Record: `docs/plans/S38-stream-resilience.md`.

**S35, 2026-09-22 — remembered devices: pair once, connect on sight.** Jake's ask after every two-PC run had needed a fresh six-digit code read aloud between machines. The first finding was that it could not have been built on what was there: `peers.json` had recorded peer fingerprints since M4 and nothing ever read them back — not by oversight but because `build_pc` supplied no certificate, so webrtc-rs minted a throwaway one per connection and this PC's DTLS fingerprint changed every run; every fingerprint the file held was stale when written. So identity came first: one ECDSA P-256 key per installation in `identity.pem`, used for every connection, which makes pinning a fingerprint real authentication — DTLS completes only for the key-holder. Then the trust model (`docs/dev/trusted-peers.md`), written before code and put to Jake with its one open decision, whether a remembered sender may connect while the receiver is *not* in Start receiving. He answered **no**: remembering removes the code, not the consent. Shipped: a versioned `peers.json` (the v0 file migrated, unknown fields kept, an unreadable file moved aside rather than overwritten; matched on fingerprint only, never name — a name never recognises anything); `trusted` on the signalling offer, serde-defaulted so an older receiver fails the empty MAC and says Bye, which the sender turns into "pair with its code once and it will"; the receiver accepts a trusted offer only for a fingerprint it recognises and reports "paired" **only after DTLS has proved it**, since the fingerprint in an SDP is public — a stranger presenting a copied one is refused and named in the log; the sender checks the receiver's *answer* carries the fingerprint it remembered, so authentication is mutual and a LAN device calling itself `studio-pc` gets nowhere; the service resolves a peer *id* into name and fingerprint, and `ShareRequest::trusted` is `#[serde(skip)]` so nothing over IPC can set it. Share lists remembered PCs first (favourites, last connected) and hides the code box when one is chosen, saying the one way it can still fail; Receive lists them with a Forget that is real and says "remembered, no code" when a sender got in that way. `rcgen` is pinned with `=` because `rtc` takes its `KeyPair` without re-exporting the type. Tests: 14 on the store, 3 on identity, wire and decode tests, 10 UI tests across both screens — 283 UI, 202 core, 189 capture, all green; footprint gate green. Deferred: DPAPI-wrapping the key (trust model §4). **Owed: the two-PC pass with relay-pc2** — a code pairing, then a reconnect with none, and the standing-rule check: install over the top on both PCs, then share with no code.

**S31, 2026-09-22 — stream health, visible while it matters.** The app showed nothing about the stream it was playing; every number used to debug the second PC's picture lived in `share.log` and was read out over a chat session. A `HealthTracker` (`ui/src/lib/health.ts`) turns the engine's cumulative counters into a state with hysteresis — two damaged 500 ms windows to appear, six clean ones to clear, so a single lost packet never flashes and a quiet gap inside a burst is not a recovery. It warns on `rtp_lost` and `frames_withheld` and never on `rtp_recovered`: S30 measured 2,242 repairs with zero lost and a clean picture, and an indicator that fires on that teaches the user to ignore the one that matters. The wording never blames the network — a test asserts it — because the first time this was measured the cause was Relay's own 64 KB buffer on a 0.2 ms LAN. Drawn as an amber chip in the corner of the picture, never across it, plus a Stream health readout (fps, bitrate, latency — safe to show since B14 — audio delay, repaired, lost) that leaves with the share rather than freezing on its last counts. `docs/dev/stream-notices.md` fixes the vocabulary for the four states a stream can be in, for S38 to adopt rather than reinvent. 12 new tests. Owed: seeing the chip stay quiet on a good stream on the second PC, which is the failure mode that matters.

**S30, 2026-09-18 to 09-20 — packet loss: a 64 KB socket buffer, and a recovery path that had never once worked.** Told to measure before fixing, and the measuring earned its keep twice. The limiter was the receiver's UDP socket buffer: Windows defaults `SO_RCVBUF` to 65,536 bytes, the sender does not pace, and a 1440p keyframe leaves as one 450–590-packet burst (530–700 KB) in about 4 ms, so every keyframe overflowed it and an ordinary 83 KB frame did not fit either. At the settings that failed (1440p60, 40 Mb/s, full-motion source, wired LAN) the same build lost 746 packets in 14 s and ended the share with 64 KB, and lost **none in three minutes with 4 MB: 0 gaps, 597 holes repaired, 10,351 frames, latency p50 1.6 ms**. Windows counts socket-overflow drops nowhere — not in UDP Receive Errors, not at the NIC — which is how this hid, and how S30 talked itself out of the right answer for a day: after the first run the record said "not the buffer", on a receive count that turned out to include retransmissions; `BUGS.md` B15 keeps the wrong turn. The second finding is why a lost packet cost 10–15 s of smear. NACK and PLI were negotiated all along (the plan's premise that they were not was wrong), but recovery had never worked, for three library defaults nobody had seen because webrtc-rs logs through a crate nothing listened to: SRTP's replay window is 64 packets, 16 ms of video, so every retransmission was rejected as a replay (1,627 rejections, 14 repairs); the interceptor chain drops all received RTCP before the application, so the sender's keyframe-request listener — there since M4 — had never received one (21 sent, 0 seen); and there was no reorder buffer, so a repaired packet was appended to the wrong frame. Also found: our track loop waited on the decoder, which made webrtc-rs drop the tail of keyframes at its 256-slot track queue. Shipped: 4 MB receive buffer through a wrapper at webrtc-rs's one socket seam, 4096-packet replay window, a reorder buffer with a 40 ms hold, NACK every 10 ms, PLI forwarded to the encoder, frames withheld for at most a second while a keyframe is fetched (the first version had no limit and froze the picture until the share died — caught by relay-pc2), a loop that never waits, and a damped bitrate controller in place of per-second AIMD (two bad seconds to step down, 10 s hold, slow climb, exponentially backed-off memory of the rate that failed; a unit test counts direction changes against a hard-limited link). `RELAY_TEST_LOSS` injects loss at the socket so all of it is testable on one PC: 110 of 110 repaired; with repair blocked, 42 keyframe requests sent and 42 received. **On 40 Mb/s as the 1440p60 default:** per pixel that is ~90 Mb/s at 4K, above the brief's 40–80, so generous rather than wrong; rate was not what lost packets, so there is no loss argument for lowering it and the quality argument is S32's. Left at 40. The new receiver counters (`rtp_recovered`, `keyframe_requests`, `frames_withheld`; `rtp_gaps`/`rtp_lost` now mean unrepaired only) are what S31 should display. **Accepted 2026-09-21 on the installed r11 (`53642d2`), in-app video, 1440p60 Warzone footage at 39 Mb/s:** 0 lost, 970 repaired, every frame presented, latency p50 1.3 ms, not one warning in the log, and Jake saw "no lag, stuttering or smearing" (run E). Then the same build with the buffer forced back to 64 KB (run F): the socket queue pinned full for 37 % of three minutes, 2,242 packets repaired, still 0 lost and a clean picture — so recovery holds on a real link by itself, and the buffer makes it rarely needed. Not yet seen on two PCs because nothing ever needed them: the keyframe request and the 1 s withholding limit (loopback-proven only). Sender pacing, tolerable on a LAN with 4 MB behind it, is the first thing to revisit for Wi-Fi. Record: `docs/dev/BUGS.md` B15.
**S33, 2026-09-18/20 — time, teardown and reproducible builds.** The four bugs S29 left, each measured before and after. **B16, the second of audio delay**, was one line: the receiver asked WASAPI for a one-second render buffer and filled all of it on every wake, silence included, so every sample queued behind a full second (measured: 1000 ms in the render buffer, 0 ms everywhere else, sender packetising in 0.11 ms). Playback is now a 40 ms primed jitter queue per track with one-frame-per-480 skip/repeat slewing to follow the sender's sample clock, and never more than 20 ms in the render buffer: 40-60 ms arrival-to-endpoint, which puts audio inside lip-sync tolerance of a ~3 ms picture; `audio.buffered_ms` and its parts are in the stats line. **B14, negative latency**: the sender re-measures the clock offset every 2 s on the signalling socket, filters by round trip and smooths, and both ends stamp from a wall-anchored monotonic clock; with drift manufactured on one PC, -29.2 ms/min and 152 of 171 samples negative became -0.004 ms/min, and at a realistic 50 ppm 57 negative samples became none. **B8, the 3 s teardown** was not `pc.close()` (0.03 ms): `Runtime::drop` waits for tokio's blocking stdin read, which only returns when the core writes, so any share that ended by something other than a stdin command sat in the destructor until the deadline. The runtime is now shut down with a timeout (a regression test plays the core: old drop never exits, new exits in 0.7 s), and the sender says `Bye` so the receiver ends when the share does rather than when ICE gives up: 4.3 s to 0.11 s. **B12**: one commit built from two folders gave 0 of 4 identical binaries; with path remapping and `/Brepro`, now set by `stage-bundle.ps1`, 4 of 4, libopus included. What is still not shown reproducible (`relay-ui.exe`, the NSIS container, an unpinned toolchain) is written down with a mismatch checklist. **Owed: the two-PC confirmation** of B14/B16/B8 with relay-pc2, which this session could not start because serving a build to the LAN was blocked by its permission policy. Record: `docs/dev/BUGS.md` B8/B12/B14/B16, `docs/dev/reproducible-builds.md`.

**S29, 2026-09-17 — the stream lives inside the app.** Jake's first ask after the first real two-PC test: the received picture belongs in the Relay window, not a window of its own. The engine's window is now a frameless popup *owned by* the app window and the shell keeps it over the Receive screen's video area through moves, resizes and DPI changes, hiding it when that screen is not showing; "Pop out into its own window" gives it a frame and its own place, and closing that window puts it back rather than ending the receive. It is an owned top-level popup and not a `WS_CHILD` for one reason: the B9 capture exclusion (`WDA_EXCLUDEFROMCAPTURE`) only holds on top-level windows of the owning process, so the engine keeps every style change and reasserts the exclusion after each one, reporting the value Windows confirms rather than the one asked for. Decode and present left the window thread, which is what made embedding safe at all — a modal move/size loop used to stall the picture for the length of the drag — and the receiver finally reads `stop` on stdin (B8). Verified on one PC against a pattern stub (`RELAY_RECEIVE_STUB=1`) with two new no-input harness scripts: placement exact to the pixel, every transition with `excluded=true`, present counter climbing throughout. Then seven two-PC runs with relay-pc2 on the Windows 10 machine (r5-r10), which found what one PC cannot: the popped-out window could not take the foreground so Esc went to the app; a second swapchain on the same HWND fails with E_ACCESSDENIED; and a hide-then-show inside one DWM frame composes the window black — the last of which was the real cause of every "black video area" report. r10 shows the picture back on every path (X, Esc, Settings-and-back, minimise/restore), the share end reaches the app (bounded teardown; B8 still owed underneath), the B9 capture exclusion was seen working on real hardware for the first time, speech audio was clear, and RTP loss was measured at two rates (B15: rate-dependent and bursty; 30 fps / 20 Mb/s was corruption-free). Filed for their own sessions: B14 (clock offset measured once), B15 (no keyframe request on a gap), B16 (audio ~1 s late). Record: `docs/dev/inapp-stream.md`, `docs/dev/BUGS.md` B13-B16.

**S27, 2026-09-16 — H.264 beside HEVC, so receiving is free.** HEVC decode on Windows is free only on PCs whose manufacturer licensed it; on a real Windows 10 PC the free package cannot be installed. Relay being free for everyone rules that out as a requirement. The sender now offers every codec its GPU encodes in hardware and the receiver answers with what it can decode: HEVC when both can, H.264 otherwise. It is a capability, never a setting. Measured with the share's own encoder on the same frames: at 4K60 40–65 Mb/s, H.264 needs about +9–11 % bitrate by VMAF (+16–21 % by PSNR) for the same picture, far less than the 30–50 % expected, but +69 % at 10 Mb/s. It encodes 1–3 ms faster than HEVC on the RTX 3090, and CPU is indistinguishable, so the latency budget improves rather than regresses. Recording writes `avc1` (fMP4) and `V_MPEG4/ISO/AVC` (MKV). B1 (fps cap never applied), B3 (receiver errors reported as timeouts) and B6 (the paywall banner) were fixed in the same files. Pending: the acceptance run to the Windows 10 PC that has no HEVC decoder. Record: `docs/plans/M4-share.md`, S27.

**S22, 2026-09-15 — the Windows Firewall rule, so "zero network config" is true.** Windows prompts the first time a given *path* listens, and dismissing that prompt writes a permanent Block rule; every symptom afterwards looks like a dead network, so the user checks their router instead. This dev machine had accumulated ten Block rules and no Allow rule. Relay now (a) adds one inbound Allow rule for `relay-share.exe` — the only binary that listens — on **private and domain networks, never public**, through the same elevated helper and the same readable UAC prompt as the other machine-wide changes, never a silent grab; (b) records it in `firewall.json` and removes it in the uninstall plan (`StepKind::RemoveFirewallRule`), so a leftover rule cannot survive the clean-VM diff; and (c) **detects and names the blocked state** on the Share and Receive screens in the same warn-before-you-fail shape as the HEVC banner, offering the one-click fix. Detection reads the firewall policy store as a pure string parse (no COM enumeration in the always-on core, fixture-tested against strings captured from a real machine); only the writes use `INetFwPolicy2`, in the helper, behind `RELAY_FIREWALL_ALLOW_LIVE_WRITE`. An install also removes the Block rules for our own binary, because Windows applies deny before allow and an Allow rule alone would leave the user exactly as broken. `machine-snapshot.ps1` / `snapshot-diff.ps1` now capture and diff firewall rules — verified to FAIL on a planted leftover rule — so the promise is actually enforced. Footprint gate still PASS (1.57 MB, 6.87 MB RSS, 0 % CPU); 446 workspace tests and 178 UI tests green. Deferred, unchanged: the clean-VM checkpoint run itself.

**S6, 2026-09-14 — the elevated install helper landed, and both components round-tripped live.** `relay-elevate.exe` is now the only Relay binary that writes `HKLM`: the core shows the exact listing, the user approves one UAC prompt, and the helper performs only what the op enum names, re-deriving every key and DLL path itself. From the Settings cards on this dev machine the camera and the APO were each registered and removed, and the endpoint's `FxProperties` `reg export` came back **byte-identical** to the pre-install export — which promotes M3b's byte-for-byte restore claim from fixture-proven to live-proven for the registry half, and closes M7's "live removal of the two opt-in components". Declining the prompt was verified to change nothing and say so. Two real defects fell out: `RegCreateKeyExW(KEY_WRITE)` is denied on an endpoint's `FxProperties` even when elevated (administrators get `SetValue` without `CreateSubKey`, so the fix was to ask for less, not to take ownership), and the uninstaller's elevated phase had been passing the live-write gates through an environment block that elevation does not inherit. Evidence and runbook: `docs/dev/elevation-live.md`. Still deferred, unchanged: loading the APO into audiodg (test-signing VM + EV cert).

**S25, 2026-09-15 — the UI became keyboard-operable, and destructive actions got one shape.** The app was mouse-only: rail entries were anchors with no `href`, `Toggle` put `role="switch"` on a non-focusable inner div, profile rows were `<tr onClick>`, and no control drew focus. They are real buttons now — the rail carries `aria-current`, the whole toggle row is a `role="switch"` button whose label and sub-line are its accessible name, and a profile row has a named button to open it and another to apply it. One `:focus-visible` rule in the champagne accent covers everything, and the shell's global `user-select: none` is relaxed for the text that exists to be pasted elsewhere: paths, monitor ids, the pairing code, readouts and error messages.

Four confirmation patterns became one. The Profiles two-step won: `ConfirmButton` arms on the first press, fires on the second, and disarms on Escape, on blur, and after four seconds. Preset delete (instant), hardware removal (a native `window.confirm` inside a window with custom chrome) and "Restore original state now" (no confirmation at all, and no `.catch`, so a refusal was indistinguishable from success) all go through it; the restore now reports both outcomes. `window.confirm`/`alert`/`prompt` throw in the test harness and a test scans the sources, so a native dialog cannot come back quietly.

Two smaller things that were losing user work or hiding failures. An unsaved per-game edit now lives outside the React tree (`ui/src/lib/drafts.ts`), so leaving the screen keeps it and the focused game changing mid-edit no longer overwrites it — it says which profile the edit belongs to and offers Save or a two-step Discard, and the rail marks it. And every screen uses one `errText()` (`ui/src/lib/err.ts`) instead of `String(e)`, which rendered `[object Object]` for every non-string rejection; errors now appear beside the control that failed and can be dismissed. 203 UI tests (up from 170), including `keyboard.test.tsx`, `confirm.test.tsx` and `unsaved.test.tsx` — all still jsdom, so nothing touches the real desktop.

**S23, 2026-09-15 — the app no longer opens dead, and the background story is told.** Autostart is off by default and the UI never started the core, so the sequence every new user performs — install, reboot, open Relay — ended with every screen reporting a dead service and a terminal command as the only remedy. The shell now starts the core itself through the same `relay-svc.exe` the installer and the Run key use, and waits for the pipe; `startup::StartError` has one variant per remedy (broken install / launch blocked / started but silent) and no catch-all, because a catch-all is the message the session existed to remove. No user-facing string names a CLI binary any more — a unit test and a UI test both assert it — and the surrounding "Core offline" jargon went with it. The core's `notice` events, stored and expired for 4 s with nothing rendering them since M0, now stack as toasts. **The DoR question is answered: a tray icon owned by the core, not the UI** — closing the window must free the Tauri process during gaming, so a UI-owned tray would die exactly when it is the only thing left saying a profile is applied. It hangs off the winloop's existing hidden window, survives an Explorer restart, and its Quit goes out through the ordinary shutdown path, which already restores, so it cannot leave a game profile applied. Close behaviour is a preference (`data/settings.json`), defaulting to keeping Relay running, with a plain line in Settings saying what stays up and where to find it. Footprint re-measured: binary 1.51 → 1.53 MB, RSS unchanged within run-to-run variance, CPU 0 %. Record and reboot evidence: `docs/dev/never-dead.md`.

**S24, 2026-09-16 — the UI stopped drawing things it had not measured.** Three places rendered invention as data. The EQ graph's dashed "Headset raw response" was a fixed path, shown for every headset including ones with no curve, and mislabelled even in principle: `autoeq.rs` stores AutoEQ's *correction*, not the raw response. It is now the imported curve on a real log-frequency axis, labelled as a correction, and absent without one; the profile line beside it, formerly straight segments between slider values, is the peaking cascade's actual response. The Display A/B was two copies of one drawn scene, so the colour sliders changed nothing on it. The decision there was real-where-exact: both halves are a grey/primary reference pattern and the right one runs through a TypeScript port of `gamma::build_ramp`, pinned to the Rust by shared golden samples, while a plain note says vibrance and hue — applied by the vendor driver, whose maths Relay does not have — are not previewed, rather than faking them with a CSS filter. The Share overlay's `Up to 3840×2160 · 60 fps` and the strip's `NVENC` came from nowhere; they now come from the preset (idle), the started preset plus the engine's measured fps (sharing), and the probe's encoder list, with a label left out when it cannot be backed. The painted `.scene` gradients on Share and Receive are gone: an empty frame is the honest placeholder.

**S26, 2026-09-16 — shell polish: the window behaves like a Windows app.** The window now reopens where it was left, maximised if it was, from `data\window.json`, written by the UI process alone. The core neither reads nor links it, and the footprint gate re-measured PASS at 1.59 MB, 8.87 MB RSS, 0 % CPU. Placement uses the normal bounds from `GetWindowPlacement`.
